# Phase 2/3/4：內容 SSOT、學習歷程與學習大廳——第三章垂直切片 Design

- 日期：2026-08-10
- 狀態：草案待 owner 核准
- 對應：`docs/roadmap-colorplay-next.md` Phase 2（內容 SSOT 與版本發布）／Phase 3（學習歷程與評量權威）／Phase 4（學習大廳與章節體驗）。三者目前狀態皆為「決策已拍板、spec 未開始」，本文件是三者的第一份正式 spec。
- 來源：owner 2026-08-10 深夜 brainstorming（涵蓋內容 pipeline 現況盤點、教師端功能盤點、JRPG 視覺方向討論，含真實截圖與 Codédex 參考圖比對）。
- **範圍提前候併說明**：roadmap 原始劃分中，教師端與 Live 相關視覺工作屬於 **Phase 5（Live 與教師報表）**，不是 Phase 4（Phase 4 原本專指學生端學習大廳/章節體驗）。Owner 在本次 brainstorming 中明確要求把教師端（含 Live）一併納入這次規劃，因此本文件第 4.3 節「教師端交付項目」實質上是**提前候併 Phase 5 的範圍**到這次一起做，不是重新定義 Phase 4 的邊界。`docs/roadmap-colorplay-next.md` 的 Phase 5 狀態列需同步更新，標明其教師端/Live 視覺部分已隨本文件提前執行。Phase 6（全站 JRPG 視覺統一）維持原範圍不變——本文件不處理次要頁面（如 `/forgot-password`、`/unauthorized`）的最終掃尾統一。

## 1. 策略：以第三章為垂直切片

Phase 2/3/4 各自獨立立 spec、走各自的 plan／worktree／review 週期，**不互相排隊**——哪個先準備好就先動。但三者的第一個交付目標統一鎖定在**第三章（色彩表示）**：把「內容匯入 → 學習歷程判定 → 章節體驗畫面」整條路徑在第三章上完整跑通一次，驗證出來的元件/測試模式，後續 5 章內容陸續到位時直接套用。

選第三章的原因：在 Sheet 重構前的舊 pipeline 下，它是唯一有實質內容量的章節（曾量測到 37 題、涵蓋 3 個小節），且已是 UI 上唯一「可進入」的章節。Sheet 重構後確切題數需等 2.2 節的匯入 pipeline 更新完成、重新跑一次 `content:fetch` 才能確認，本節數字僅供選定切片對象的背景依據，不作為驗收基準。

## 2. Phase 2：內容 SSOT 與版本發布

### 2.1 背景：Sheet 結構已重新設計

Owner 在本次規劃期間已將 Google Sheet 重構為 5 個分頁，且加入全域唯一序號欄位：

| 分頁 | 主要欄位 | 狀態 |
|---|---|---|
| 各單元複習大廳 | 複習卡序號／章節／章節標題／小節／小節標題／子主題／子主題標題／卡片內容／附件 | 本次範圍 |
| 各單元隨機測驗題庫（小節測驗題庫） | 題庫序號／章節／小節／題目／選項A-D／正確答案／解析 | 本次範圍 |
| 章節總複習（章節總測題庫） | 題號／章節／題目／選項A-D／正確答案／解析 | 本次範圍 |
| 前測題目 | 題庫序號／題目／A-D／解答／難度／對應章節／對應內容 | **排除，未來項目** |
| 後測題目 | 同上 | **排除，未來項目** |

現有匯入腳本（`scripts/content/fetch-sheet.mjs`／`import-questions.mjs`／`import-review-cards.mjs`／`verify-sheet-db.mjs`）是依照舊結構（單一「題庫」分頁＋`code`欄位）寫的，對新結構會直接匯入失敗（`content:fetch` 目前已實測失敗：「題庫分頁缺少必要欄位：code」）。

### 2.2 交付項目

1. **匯入 pipeline 更新**，對齊新的 5-分頁結構（前測/後測分頁讀取邏輯本次不做，明確跳過）：
   - `各單元隨機測驗題庫` 與 `章節總複習` 從單一扁平題庫拆成兩個獨立來源分別匯入，對應「小節測驗」與「章節總測」兩種題目池。
   - 欄位對應更新：`題庫序號`／`題號`／`複習卡序號` 取代舊的 `code`。
2. **`產生題目識別碼` Google Apps Script**（`docs/roadmap-colorplay-next.md`「Approved content and publication decisions」已核准機制的具體落地）：
   - 綁定 Sheet 的 Apps Script command，對新題目/卡片列自動產生**全域唯一**序號，寫入受保護欄位，不重新計算既有值。
   - 序號欄位＝永久識別碼欄位，兩個概念統一為一個機制（不是兩套並行的 ID）。
   - 網站與匯入器僅讀取並驗證序號，不寫回 Sheet。
   - 交付物包含 owner 設定引導文件：安裝腳本、保護欄位、授權範圍、驗證「產生」與「拒絕重複」行為。
3. **複習卡多卡支援**：改用 `複習卡序號` 作為卡片識別碼（取代原本以「小節:子主題:標題」雜湊出的識別碼），原生支援同一子主題下多張獨立卡片（如色相／明度／彩度各自獨立成卡）。
   - 顯示規則：卡片標題顯示**子主題標題**；同子主題下多張卡標題相同，僅靠複習卡序號排序區分先後。
4. **兩層品質關卡正式納入 Definition of Done**（機制已存在，此次是正式文件化＋要求執行）：
   - 結構層：`verify-sheet-db.mjs --gate`，錯誤即擋匯入。
   - 內容品質層：`content-reviewer` agent 依 `docs/content/question-review-rubric.md` C1-C8 準則逐題審查，LLM 初篩不修改檔案。
   - 兩層都過，該章節內容才算「完整」，不只看題目/卡片數量。

### 2.3 明確排除

- **前測／後測題目**：新內容類型，本次不處理匯入邏輯，留待未來獨立規劃。
- **教師端內容管理頁面（tContent）**：owner 裁定改放 **Admin 後台**，不在教師端範圍內，也不在本次 Phase 2/3/4 的實作範圍——僅在此記錄這個決策，實際 Admin 頁面設計另立 spec。

## 3. Phase 3：學習歷程與評量權威

範圍最小，核心邏輯（`chapter_sequence_access`／循序解鎖／精熟度計算）已存在於 migration 中，但截至今晚才第一次補齊到 staging（先前落後 13 個 migration，且有 9 個歷史分岔，已於 2026-08-10 修復並驗證同步）。

### 3.1 交付項目

1. 正式撰寫 spec，把現有機制（章節完成三條件：複習卡全完成／小節精熟≥80%／章節總測精熟≥80%）文件化為可核准的規格,對齊 `docs/roadmap-colorplay-next.md`「Approved learning progression decisions」。
2. RLS 負向測試：非本人/非該班教師存取章節進度、越權解鎖等情境。
3. 以第三章實跑一次完整驗收流程：小節複習完成 → 小節測驗精熟 → 章節總測精熟 → 章節完成 → 第四章解鎖狀態正確反映（即使第四章內容仍「準備中」，解鎖旗標本身要正確）。

## 4. Phase 4：學習大廳與章節體驗

### 4.1 視覺方向：插畫場景 ＋ Codédex 式清單卡片（混合）

Owner 提供 Codédex（程式學習平台）截圖作為暗色系參考：深色扁平卡片、像素點陣標題字、編號關卡路徑、鎖定內容用「???」佔位、細框線、右側個人資料/進度/徽章卡。與現行 ADR 0005「插畫式 JRPG 世界」（村莊地圖、羊皮紙質感、木紋公會榜）方向不同，比對後決定採**混合方向**，不整個推翻 ADR 0005：

- **探索／場景類頁面**（學習大廳村莊地圖、章節內部場景）：維持插畫世界，但整體改成**夜間色調**（沿用登入頁既有的 `scene-night` 星空語彙，不是重新設計一套插畫）。
- **清單／進度類頁面**（小節任務清單、複習卡列表）：改成 **Codédex 式深色扁平卡片**——深色卡片＋細框線＋像素點陣標題字＋編號圓圈連成的關卡路徑＋鎖定內容用「???」樣式。理由：這類頁面本質上是「關卡清單」，跟參考圖的用途最接近，插畫化的價值最低。

### 4.2 學生端交付項目

1. **`chapter-detail-page`（章節體驗）改版**——目前唯一 0% JRPG 化的學生端核心頁面。第一次用第三章的真實內容驗收（複習卡、小節精熟度、章節總測入口）。套用 4.1 的清單/進度頁面視覺方向。
2. **手機版策略統一**：全站改成**直向＋左右滑動／捲動**，不強制轉橫。移除「小節任務選擇頁」目前的強制轉橫提示，改成跟學習大廳一致的滑動模式。
3. **累積/總體正確率數字收起**：學生端不再顯示「累積正確率 X%」這類彙總統計數字。**維持顯示**：逐題即時對/錯回饋、精熟度過關門檻（如「精熟度 18.9% / 80%」，這是學習機制必要的進度指標，不是彙總統計）、錯題複習時的正確答案與解析。精確邊界（哪些畫面的哪個數字算「彙總統計」、哪些算「機制必要」）於實作 plan 階段逐頁條列確認，避免遺漏邊界情況。
4. **已知缺陷修復**：
   - 學習大廳村莊地圖手機版（375px）Chapter 2/5 建築標籤文字被螢幕邊緣裁切——若地圖設計上本來就是可橫向捲動，需確認捲動實際可用且不誤裁邊界內容；若捲動無法完整看到，仍視為需修的版面錯誤。
   - 班級排行榜表頭錯字「曜稱」→「暱稱」。
5. **既有已完成頁面的按鈕/卡片風格基準**：以商店（`/app/shop`）與成就（`/app/achievements`）兩頁的按鈕狀態設計（已裝備／可購買／點數不足三種樣式）為基準，其餘頁面的按鈕/卡片風格往這個方向對齊。

### 4.3 教師端交付項目（提前候併 Phase 5 範圍，見文件開頭說明）

1. **補完既有已核准的 08-02「賢者工坊」設計**（`docs/superpowers/specs/2026-08-02-teacher-workspace-design.md`，owner 已核准；對應 plan `docs/superpowers/plans/2026-08-02-teacher-workspace.md`）尚未完成的部分。註：該 plan 的 checkbox 全數未勾但程式碼證明部分工作已完成，執行前需先以程式碼實際狀態（而非 checkbox）重新核對剩餘範圍，已知尚未觸及：
   - 教學分析（`/teacher/analytics`）
   - 班級管理列表（`/teacher/classes`，含 GamePager 分頁與木牌卡樣式）
   - Live 建立頁（`/teacher/live`，召集令語彙）
   - Live 報表（`/teacher/live/:sessionId/report`）的名次獎牌符號
   - HUD 教師導覽列（Link→NavLink、active 態、面板恆掛 DOM、click-outside 關閉、焦點管理）
2. **教師端 Live 功能改採完整 JRPG 像素風**（不是賢者工坊低濃度處理）——`/teacher/live`、`/teacher/live/:sessionId`（含投影模式）、`/teacher/live/:sessionId/report`。理由：Live 是教師與學生共享的即時體驗，學生端已是完整像素風格的「公會團體戰」語彙，教師端維持一致濃度才不會視覺斷裂。
   - **正式覆蓋 08-02 的 LivePresenter 零接觸規則**：`docs/superpowers/plans/2026-08-02-teacher-workspace.md` 原本明訂 `src/features/live/components/live-presenter.tsx`（教師 Live 投影主持台）零接觸、不改任何一行，理由是既交付投影元件、誤動風險高。Owner 2026-08-10 明確裁定：**投影畫面的視覺樣式可以改，但比照本文件所有其他 JRPG 改版項目同一條「純表現層、行為零變更」原則**——狀態機、RPC、按鍵觸發的動作、主持流程順序一律不動；只有外觀（顏色、邊框、字體、版面語彙）改成 JRPG 像素風。改版時涉及按鍵/流程配合視覺調整的部分，實作階段會搭配前端 UI 相關 skills 協助完成，但仍受「行為零變更」約束。
   - **測試風險**：`tests/e2e/assignments-live.spec.ts`／`live-advanced.spec.ts` 先前已因 Live 互動模型改版部分失效（詳見 `docs/superpowers/plans/2026-08-02-red-spec-sizing.md` 的斷差盤點），LivePresenter 這次真的被觸碰，紅測試範圍大機率會再擴大，需要在實作 plan 裡一併估工。
3. **Dashboard 功能捷徑補齊**：目前「功能捷徑」只連到教學分析／班級管理兩處，遺漏 Live。導覽資訊架構需要跟著新增/確認的教師功能同步更新。
4. **學生進度頁（`/teacher/classes/:classroomId/members/:memberRef`）新增**：
   - 「Live 參與紀錄」區塊，與現有「各章節學習進度」表格並列——場次數、每場次正確率／名次。
   - 正確率拆分為「課堂 Live」與「課後自主」兩欄，取代現有單一混合正確率。
   - 此區塊資料**僅教師可見**，對應 4.2 第 3 點的學生端收斂規則——同一份數據，教師端完整呈現、學生端只留機制必要的部分。

### 4.4 明確排除／未來項目

- **教師評分／評語功能**：owner 提出但決定本次不設計細節,記錄為未來項目。資料模型、可見範圍、與既有客觀指標（XP/精熟度/排名）的關係，留待該功能正式立案時再討論。
- **視覺 token 細節**（確切顏色、間距、字重）：本 spec 只定方向（4.1 的插畫/扁平卡混合策略），實作階段會搭配前端 UI 相關 skills（如 frontend-design、ui-ux-pro-max）產出實際視覺稿。

## 5. 跨 Phase 依賴與驗收

- Phase 2 的複習卡序號機制是 Phase 4 章節體驗頁能正確顯示多張獨立卡片的前提；Phase 3 的章節完成判定是 Phase 4 章節卡「已精熟／學習中」狀態顯示正確的前提。三者透過**第三章**這條共同驗收路徑對齊，不需要嚴格的「Phase 2 全部完成才能開始 Phase 4」這種順序依賴。
- 第三章垂直切片的 Definition of Done：
  1. 內容：`content:fetch`／`content:verify` 對新 Sheet 結構跑通、兩層品質關卡皆過、複習卡以序號正確排序顯示。
  2. 學習歷程：staging 上實跑一次第三章完整解鎖流程,含 RLS 負向測試通過。
  3. 畫面：`chapter-detail-page` 完成改版並以第三章真實內容驗收；教師端能在學生進度頁看到某學生第三章的課堂/課後拆分數據。
